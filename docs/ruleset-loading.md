# Загрузка и горячая перезагрузка ruleset

Как приложение читает `/etc/dns-override/ruleset.dat`, как часто и что делает при ошибках.
Формат файла — [`ruleset-format.md`](ruleset-format.md).

---

## 1. Конфигурация самого приложения

В штатном `dnsApp.config` Technitium (правится из админки и через
`POST /api/apps/config/set`) лежит только указатель:

```json
{
  "rulesetPath": "/etc/dns-override/ruleset.dat",
  "runtimeStatePath": "/etc/dns-override/runtime-state.json",
  "enabled": true,
  "appPreference": 20,
  "watch": { "debounceMs": 500, "pollIntervalSec": 60 }
}
```

`enabled: false` — аварийный тумблер прямо из админки Technitium: приложение
возвращает `null` на все запросы, не трогая файл правил.

`appPreference` (0..255) — значение `IDnsApplicationPreference.Preference`:
DNS-сервер сортирует по нему установленные приложения, меньшее значение
опрашивается раньше. Приложение без этого интерфейса сервер считает за `100`.
По умолчанию у DNS Override — `20`, как у штатного NX Domain App.

`watch.debounceMs` зажимается в 50…60000, `watch.pollIntervalSec` — в 5…3600.
Отсутствующие поля берутся по умолчанию, лишние игнорируются.

Битый конфиг приложение отвергает исключением. Это осознанно: `SetConfigAsync`
в Technitium сначала вызывает `InitializeAsync` и только потом записывает файл,
поэтому некорректный JSON из админки просто не сохранится, а работать продолжит
прошлая конфигурация.

Всё остальное — targets, `qtypePolicy`, `defaultAction` — приходит в заголовке
самого ruleset. Второго источника настроек нет.

## 2. Когда читается файл

| Триггер | Когда срабатывает | Что делает |
|---|---|---|
| `InitializeAsync` | старт приложения, установка/обновление, изменение `dnsApp.config` | полная загрузка |
| `FileSystemWatcher` | бот заменил файл | загрузка после дебаунса |
| Страховочный таймер | раз в `pollIntervalSec` (по умолчанию 60 с) | `stat`, загрузка только если файл изменился |
| DNS-запрос | — | **никогда**; только поиск в памяти |

В типичной работе: одно чтение файла на каждое изменение от бота плюс один
дешёвый `stat` в минуту.

### Watcher — на каталог, не на файл

Бот пишет `ruleset.dat.tmp` и делает `rename()`. Это **замена inode**: watcher,
подписанный на сам файл, после первой же записи следит за удалённым inode и больше
никогда не срабатывает.

Поэтому `FileSystemWatcher` вешается на **каталог** `/etc/dns-override`
с `Filter = "ruleset.dat"` и `NotifyFilter = FileName | LastWrite | Size`.
Интересуют события `Created`, `Renamed`, `Changed`.

### Дебаунс

События приходят пачкой (`Created` + `Renamed` + `Changed`). Таймер на
`debounceMs` (500 мс) перезапускается на каждом событии; загрузка стартует, когда
поток событий утих. Одна перезагрузка вместо трёх.

### Страховочный опрос

`inotify` не работает на части монтирований: bind-mount из другого namespace,
docker volume, NFS, SMB. Раз в `pollIntervalSec` приложение делает `stat` и сравнивает
`(mtime, size)` с запомненными. Совпало — выходит немедленно, файл не открывается.
Стоимость — один системный вызов в минуту.

Опрос также закрывает гонку «watcher переподписался и пропустил событие»
и восстановление после сбоя inotify-очереди (`IN_Q_OVERFLOW`).

## 3. Как читается

```
open(O_RDONLY) → строка заголовка → парс JSON → проверка сигнатуры и version
      → потоковое чтение тела в буфер, попутно sha256
      → сверка count и sha256 с заголовком
      → построение снапшота → атомарная подмена ссылки
```

1. **Заголовок.** Читается первая строка. Сигнатура не `!DNSOVR1` или
   `version` больше поддерживаемой — загрузка прекращается сразу, файл не читается дальше.
2. **Тело.** Читается одним `ReadAllBytes`/`FileStream` в `byte[]` (домены —
   ASCII/punycode, поэтому байты, а не строки). Попутно считается sha256.
3. **Проверка целостности.** `count` и `sha256` сверяются с заголовком.
   Не сошлось — файл отвергается целиком. Это ловит момент, когда файл читается
   в процессе записи (при неатомарной записи или при копировании через `cp`).
4. **Снапшот.** Тело остаётся одним `byte[]`; строится `int[] lineOffsets`.
   Дерево не строится: файл уже отсортирован ботом.
5. **Подмена.** `Volatile.Write(ref _snapshot, newSnapshot)`. Обработчики
   запросов читают поле без блокировок, начатые запросы дорабатывают на старом
   снапшоте, он уходит в GC. Сами загрузки сериализованы семафором.
6. **Побочные действия.** Перезапись `runtime-state.json` (тем же `tmp` + `rename`)
   и запись в лог Technitium. Сброс кэша приложение не делает — см. §7.

Разбор строки и проверка порядка сортировки идут одним проходом по телу: в уже
отсортированном файле дубликаты обязаны лежать рядом, поэтому достаточно сравнения
с предыдущей строкой. Проверяется то же, что и в `tools/check-ruleset.py`:
раскладка строки, диапазон `targetIndex`, `action=P` → `targetIndex=0`, порядок,
дубликаты, длины и алфавит меток.

### Структура снапшота в памяти

| Поле | Что |
|---|---|
| `byte[] body` | тело файла как есть |
| `int[] lineStart` | смещение начала каждой строки |
| `Header header` | распарсенный заголовок, targets, qtypePolicy |

Поиск: для каждого суффикса QNAME (от самого длинного) — бинарный поиск по
`lineStart` со сравнением `ReadOnlySpan<byte>` прямо в `body`.
**Ноль аллокаций на запрос**, `O(меток × log n)`.

Расход памяти ≈ размер файла + 4 байта на правило.
300k правил ≈ 8 МБ тела + 1.2 МБ индекса ≈ **10 МБ**. Во время перезагрузки
кратковременно живут два снапшота — пик вдвое выше.

## 4. Ошибки

Принцип: **никогда не отдавать наружу полузагруженное состояние**. Любая ошибка →
продолжает работать предыдущий снапшот.

| Ситуация | Поведение |
|---|---|
| Файла нет при старте | снапшота нет, все запросы уходят в passthru; ошибка в `runtime-state.json` |
| Файла нет после успешной загрузки | снапшот сохраняется, файл не считается удалённым (это обычная фаза `rename`) |
| Неизвестная сигнатура / `version` | загрузка отклонена, прошлый снапшот жив |
| Битый JSON заголовка | то же |
| `count` или `sha256` не сошлись | то же; повтор при следующем событии |
| `targetIndex` вне диапазона | вся загрузка отклонена — приложение не чинит битые ссылки |
| Тело не отсортировано или содержит дубль | загрузка отклонена: на неотсортированном теле бинарный поиск неверен |
| Нет прав на чтение | загрузка отклонена, ошибка с явным упоминанием прав |
| Файл исчез на мгновение (окно `rename`) | до трёх попыток чтения с паузой 100 мс |
| `engine.enabled: false` | файл загружен, но на все запросы возвращается `null` |
| `enabled: false` в `dnsApp.config` | файл не читается вообще, watcher не запускается |

Все ошибки пишутся в `runtime-state.json` → `errors[]` (последние 10, каждая
с меткой времени) и в лог Technitium. Бот показывает их в разделе статуса.
Успешная загрузка список ошибок очищает — файл описывает текущее положение дел.

Отвергнутый файл не перечитывается по кругу: приложение запоминает его
`(mtime, size)` и ждёт следующей записи от бота.

Приложение **не откатывается** на резервную копию файла и не пытается его чинить:
единственный писатель — бот, он же и должен переписать файл корректно.

## 5. Обратный канал: `runtime-state.json`

Пишет приложение, читает бот. Конфигом не является.

```json
{
  "appVersion": "0.1.0",
  "startedAt": "2026-08-09T08:59:01Z",
  "lastLoadAt": "2026-08-09T12:35:01Z",
  "lastLoadDurationMs": 214,
  "lastLoadTrigger": "watcher",
  "appliedRevision": 128,
  "rulesLoaded": 312455,
  "targetsLoaded": 3,
  "snapshotBytes": 9863241,
  "rulesetMTime": "2026-08-09T12:35:00Z",
  "enabled": true,
  "errors": [],
  "stats": { "queriesTotal": 184213, "overridden": 9142, "passthru": 175071, "nodata": 3388, "nxdomain": 12, "refused": 0, "since": "2026-08-09T08:59:01Z" }
}
```

| Поле | Значение |
|---|---|
| `lastLoadTrigger` | `init` \| `watcher` \| `poll` — чем вызвана последняя загрузка |
| `appliedRevision` | `revision` из заголовка загруженного файла; `null`, если файл ни разу не загрузился |
| `enabled` | итоговое состояние: `enabled` в `dnsApp.config` **и** `engine.enabled` в ruleset |
| `errors[]` | строки вида `<ISO-время> <сообщение>`, последние 10 |
| `stats.since` | момент старта приложения; счётчики не переживают перезапуск |

Файл перезаписывается после каждой загрузки правил и на каждом тике страховочного
опроса (по умолчанию раз в 60 с) — так счётчики не устаревают.

Бот после записи ruleset ждёт, пока `appliedRevision` не сравняется с `revision`
из заголовка. Не сравнялся за 10 секунд — предупреждение оператору: приложение
выключено, нет прав на файл, или не работает watcher.

## 7. Сброс кэша DNS делается вручную из бота

После смены правил в кэше DNS-сервера остаются старые ответы. Приложение сбросить
их **не может**: `IDnsServer` не содержит операции сброса, а `IDnsServer.DnsCache` —
это `IDnsCache` с двумя методами, `QueryAsync` и `CacheResponse`. Ни удаления
записи, ни очистки кэша там нет.

Автоматического сброса нет и на стороне бота. Кэш сбрасывает оператор кнопкой
**🧰 Сервис → 🧹 Сбросить весь кэш DNS**, которая дёргает `POST /api/cache/flush`
(метод описан в `APIDOCS.md` Technitium). Сбрасывается весь кэш резолвера целиком.

Почему так: точечное удаление (`/api/cache/delete?domain=…`) требовало бы хранить
диф прошлой сборки и делать по запросу на домен, а ронять весь кэш резолвера
без ведома оператора — не то решение, которое стоит принимать автоматически.

Полей `flushCacheOnReload` и `flushScope` в заголовке ruleset больше нет.
В файлах от ранних версий бота они ещё встречаются — приложение их игнорирует
как любые другие неизвестные поля.
