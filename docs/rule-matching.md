# Семантика правил: что делает бот, что делает приложение

Разделение обязанностей жёсткое:

| | Бот (компилятор) | Приложение (исполнитель) |
|---|---|---|
| Источники, списки, приоритеты | ✅ знает | ❌ не знает |
| Дедупликация, разрешение конфликтов на одном домене | ✅ делает | ❌ не делает |
| Нормализация доменов правил | ✅ делает | ❌ не делает |
| Разбор по длине суффикса (wildcard/apex) | ❌ невозможно | ✅ делает |
| Формирование DNS-ответа | ❌ | ✅ |

Причина, по которой часть логики нельзя унести в бота, — в §3.

---

## 1. Термины

| Термин | Значение |
|---|---|
| `override` | «подменять» — ответить адресами из `target`, не ходить к апстриму |
| `passthru` | «не подменять» — вернуть `null`, Technitium резолвит запрос как обычно |
| `wildcard` (`W`) | правило покрывает **сам домен + поддомены любой глубины** |
| `apex` (`A`) | правило покрывает **только сам домен** |
| `rdomain` | домен с метками в обратном порядке: `test.google.com` → `com.google.test` |

Домен, не попавший ни под одно правило, по умолчанию **не подменяется**
(`engine.defaultAction = "passthru"` в заголовке ruleset).

---

## 2. Что делает приложение — весь алгоритм

Приложение видит только плоский отсортированный список правил и один параметр
`defaultAction`. Никаких приоритетов, слоёв и источников в файле нет.

```
1. q = нормализованный QNAME (lowercase, punycode, без точки на конце)
2. rq = метки q в обратном порядке
3. для d от len(rq) до 1:                       # от самого длинного суффикса к короткому
       key = первые d меток rq, через точку
       найти key бинарным поиском в теле ruleset
       если найдено:
           если d == len(rq):                   # точное совпадение с доменом запроса
               подходит запись A, иначе W
           иначе:                               # запрос — поддомен
               подходит только запись W
           если подходящая запись есть → вернуть её action/target   # ПЕРВОЕ попадание побеждает
4. ничего не нашли → defaultAction
```

Три правила, и это всё:

1. **Побеждает самое длинное совпадение по суффиксу.** Цикл идёт сверху вниз и
   останавливается на первом попадании.
2. **При точном совпадении домена `apex` бьёт `wildcard`** (по контракту они лежат
   рядом, `A` перед `W`).
3. **`apex` не покрывает поддомены.** Если на глубине `d < len(rq)` нашлась только
   запись `A`, это не совпадение — цикл идёт дальше к более короткому суффиксу.

Совпадение суффикса всегда идёт по границе метки: сравниваются целые метки `rdomain`,
поэтому `evilgoogle.com` не совпадает с правилом на `google.com`.

Сложность: `O(меток × log n)` — около 8 бинарных поисков на запрос, независимо
от размера списка. Реализация загрузки и поиска —
[`dns-override-technitium-app/docs/ruleset-loading.md`](ruleset-loading.md).

### 2.1 Примеры

Ruleset (уже скомпилирован ботом):

```
WP0 com.google              # google.com + поддомены → не подменять
WO0 com.google.test         # test.google.com + поддомены → подменять
AO1 org.example             # только example.org → подменять через target[1]
```

| Запрос | Найденный суффикс | Результат | Почему |
|---|---|---|---|
| `google.com` | `com.google` (d=2, точное) | passthru | запись `W`, `A` нет |
| `www.google.com` | `com.google` (d=2, поддомен) | passthru | `W` покрывает поддомены |
| `test.google.com` | `com.google.test` (d=3) | **override** | первое попадание — самое длинное |
| `a.b.test.google.com` | `com.google.test` (d=3) | override | |
| `example.org` | `org.example` (d=2, точное) | **override** | точное совпадение, запись `A` подходит |
| `www.example.org` | — | passthru (default) | `A` не покрывает поддомены, короче ничего нет |
| `evilgoogle.com` | — | passthru (default) | не граница метки |
| `google.com.ru` | — | passthru (default) | другой суффикс |

## 3. Почему разбор суффиксов нельзя унести в бота

Логичный вопрос: если бот всё разруливает, почему бы не отдать приложению плоский
список «домен → действие» с точным совпадением?

Потому что `wildcard` покрывает **бесконечное** множество поддоменов. Правила

```
google.com       → passthru
test.google.com  → override
```

нельзя развернуть в перечисление: `a.test.google.com`, `b.test.google.com`, … —
их неограниченно много и они заранее неизвестны. Любой конечный список неизбежно
промахнётся по домену, которого в нём нет.

Поэтому граница проведена так: **бот убирает всё, что зависит от происхождения правил;
приложению остаётся чистая иерархия доменов**, которая от происхождения не зависит.
Требование «приложение не знает, как собираются правила» выполняется полностью.

## 4. Что делает бот при компиляции

Подробности — [`ruleset-compile.md`](https://github.com/Ashteeer/dns-override-telegram-bot/blob/main/docs/ruleset-compile.md).
Здесь только итоговые правила, потому что они определяют поведение системы.

### 4.1 Синтаксис `@`

| Ввод пользователя | Домен | `scope` |
|---|---|---|
| `google.com` | `google.com` | `wildcard` |
| `@google.com` | `google.com` | `apex` |

Правила из внешних списков — **всегда** `wildcard`, `@` в них игнорируется.

### 4.2 Нормализация домена

Выполняется ботом до записи в ruleset. Приложение те же шаги применяет к QNAME запроса —
поэтому расхождение в реализации приводит к молча несрабатывающим правилам.

1. Обрезать пробелы и обрамляющие кавычки.
2. Снять ведущий `@` (→ `scope = apex`), ведущие `*.` и `.` (→ `scope = wildcard`).
3. Если строка похожа на URL — снять схему, путь, порт (`https://a.b:443/c` → `a.b`).
4. Нижний регистр.
5. IDN → punycode по UTS-46 (IDNA2008, `UseStd3AsciiRules = true`): `сайт.рф` → `xn--80aswg.xn--p1ai`.
6. Снять завершающую точку.
7. Отбросить, если: пусто; > 253 байт; метка > 63 байт; метка начинается или
   заканчивается на `-`; после punycode есть символы вне `[a-z0-9.-]`; это IP-адрес.

Защищённые зоны, которые бот отказывается принимать в правила: корень `.`,
односоставные TLD (`com`, `ru`, …), `in-addr.arpa`, `ip6.arpa`, `local`, `localhost`.

### 4.3 Разрешение конфликтов при компиляции

Конфликт — это две и более записи на **одну и ту же пару (домен, scope)**.
Разные домены не конфликтуют: их разберёт приложение по длине суффикса.

Победитель выбирается по критериям в порядке:

| № | Критерий | Что выигрывает |
|---|---|---|
| 1 | `priority` | больше. Правила пользователя — `1000`, источники — своё поле `priority` (по умолчанию `0`) |
| 2 | `action` | `override` (настраивается: `override-wins` / `passthru-wins`) |
| 3 | *(fallback)* | меньший `id` — только ради детерминированности сборки |

Порядок критериев и tie-break задаются в конфиге бота.

Пример из ТЗ: пользователь задал `google.com → passthru` и `test.google.com → override`.
Это **разные домены**, конфликта нет — обе строки попадают в ruleset как есть,
а нужное поведение («google.com не подменяем, test.google.com подменяем») даёт
разбор по длине суффикса в приложении (§2.1).

Пример настоящего конфликта: список требует `google.com → override`, пользователь —
`google.com → passthru`. Одна пара (домен, scope), побеждает пользователь по `priority`,
в ruleset уходит одна строка `WP0 com.google`.

### 4.4 `@` против домена из списка — разный scope, конфликта нет

Случай, который легко понять неправильно. Правила из списков **всегда** `wildcard`,
поэтому `@` в пользовательском правиле делает пару (домен, scope) **другой**,
и приоритет не применяется — обе строки попадают в файл:

| Источник | Правило | Строка в ruleset |
|---|---|---|
| список из интернета | `google.com` → override | `WO0 com.google` |
| правило пользователя | `@google.com` → passthru | `AP0 com.google` |

Результат разбирает приложение по §2:

| Запрос | Результат | Почему |
|---|---|---|
| `google.com` | **passthru** | точное совпадение, `A` лежит перед `W` и выигрывает |
| `www.google.com` | **override** | `A` не покрывает поддомены, срабатывает `W` из списка |
| `test.google.com` | **override** | то же самое |
| `a.b.test.google.com` | **override** | то же самое |

То есть `@google.com → не подменять` снимает подмену **только с самого `google.com`**,
поддомены остаются под правилом списка. Это и есть смысл `@`.

Чтобы отключить подмену для всего домена вместе с поддоменами, правило нужно задавать
**без** `@`: тогда scope совпадает со списочным, возникает настоящий конфликт,
пользователь побеждает по `priority`, и в файл уходит одна строка `WP0 com.google`.

| Что нужно | Что вводить |
|---|---|
| не подменять `google.com`, но подменять поддомены | `@google.com` |
| не подменять `google.com` и все поддомены | `google.com` |

Оба сценария закреплены тестами
`test_apex_user_rule_does_not_cancel_list_wildcard` и
`test_wildcard_user_rule_cancels_whole_list_entry`
в [`dns-override-telegram-bot/tests/test_compiler.py`](https://github.com/Ashteeer/dns-override-telegram-bot/blob/main/tests/test_compiler.py).

## 5. Формирование ответа

Победившее правило с `action = override` даёт индекс в `targets[]`.
Дальше решает `qtypePolicy` по типу запроса:

| Значение | Поведение |
|---|---|
| `target` | ответить согласно `mode` target'а |
| `nodata` | `NOERROR`, пустая ANSWER + SOA в AUTHORITY |
| `nxdomain` | `NXDOMAIN` |
| `passthru` | вернуть `null` — обычный резолв, даже если правило `override` |

Владелец SOA в отрицательных ответах: при `nodata` — домен сработавшего правила,
при `nxdomain` — его родительская зона (так же, как в штатных приложениях
Technitium). Если правило не сработало и ответ пришёл от `defaultAction=override`,
зоной считается сам QNAME.

`target` для типа, которого у `mode: address` быть не может (например
`qtypePolicy: {"MX": "target"}`), даёт `nodata`: реальный ответ не должен утечь
мимо подмены. `mode: refused` отвечает `REFUSED` без секции AUTHORITY.

По умолчанию:

```json
{ "A": "target", "AAAA": "target", "HTTPS": "nodata", "SVCB": "nodata", "ANY": "nodata", "*": "passthru" }
```

**Почему `HTTPS`/`SVCB` → `nodata`.** В этих записях лежат `ipv4hint`/`ipv6hint` и ECH-конфиг.
Пропустив их мимо подмены, браузер возьмёт реальные адреса из хинтов и уедет напрямую
в обход подменённых A/AAAA — подмена молча перестанет работать.

**`emptyFamilyPolicy`** — что делать с `AAAA`, если в target нет IPv6 (и симметрично для `A`):

- `nodata` (по умолчанию) — пустой `NOERROR`, клиент уйдёт на IPv4, реальный адрес не утечёт;
- `passthru` — отдать реальный AAAA. **Дырка**: клиент с IPv6 поедет напрямую;
- `answer` — вернуть пустой ответ как есть.

Флаги ответа: `AA = true`, **`AD` всегда `false`** (подменённые данные не валидированы),
`RRSIG` для override-ответов не выдаётся никогда.

## 6. Известные ограничения

1. **CNAME-цепочки при `passthru`.** Домен пропущен без подмены, апстрим вернул `CNAME`
   на домен из ruleset — ответ уедет с реальным адресом. Закрывается отдельным
   `IDnsPostProcessor`, который прогоняет CNAME-цели через тот же поиск.
   Требует подтверждения — открытый вопрос в корневом `CLAUDE.md`.
2. **DNSSEC.** Клиент с валидацией отвергнет подменённый ответ для подписанной зоны.
   Смягчение: не ставить `AD`, не отдавать `RRSIG`. Полного решения нет — это
   принципиальное свойство подмены.
3. **DoH/DoT мимо сервера.** Браузер со своим DoH не пойдёт в Technitium. Решается
   на уровне сети, вне зоны ответственности приложения.
4. **Кэш Technitium.** После смены правил в кэше остаются старые ответы, и до истечения
   их TTL подмена на этих доменах не работает. Автоматического сброса нет: приложению
   интерфейс Technitium такой операции не даёт, а бот сбрасывает кэш только по кнопке
   и целиком. См.
   [`ruleset-loading.md §7`](ruleset-loading.md#7-сброс-кэша-dns-делается-вручную-из-бота).
