# Решения по модели конфигурации

Короткий журнал принятых решений и отвергнутых альтернатив. Менять только осознанно.

---

## D1. Приложение читает один скомпилированный файл

**Решение.** Единственный вход для приложения — `/etc/dns-override/ruleset.dat`
с уже готовыми правилами. Всю сборку (списки, пользовательский ввод, приоритеты,
дедупликация) делает бот. `dnsApp.config` содержит только путь и аварийный `enabled`.

**Почему.**
- Приложение внутри DNS-сервера должно быть максимально простым: меньше кода в горячем
  пути — меньше способов уронить резолвинг. У него остаются три операции:
  прочитать файл, найти самый длинный суффикс, собрать ответ.
- Один файл = одна атомарная замена = один согласованный снапшот. Нет ссылочной
  целостности между файлами, нет вопроса «в каком порядке писать», нет окна, в котором
  правило ссылается на ещё не созданный target.
- Логика слияния может меняться сколько угодно (новые форматы списков, роли, web-ui) —
  приложение при этом не трогается и не переустанавливается.

**Отвергнуто:**

| Вариант | Почему нет |
|---|---|
| Три файла: настройки + правила пользователя + описания источников, слияние в приложении | приложение обязано знать о приоритетах и источниках; ссылочная целостность между файлами; окно рассогласования при записи |
| Всё в `dnsApp.config` Technitium | конфиг гоняется целиком через HTTP-API и админку; на 8 МБ админка встаёт, каждая правка одного домена — round-trip мегабайтов |
| SQLite как общее хранилище | нативная зависимость `SQLitePCLRaw` внутри DNS-сервера; нет надёжного межпроцессного уведомления об изменении — нужен polling; блокировки WAL и права между двумя демонами |

**Следствие.** У бота появляется собственное внутреннее состояние
(правила пользователя, описания источников, кэш скачанных списков). Оно
контрактом **не является** и живёт в `/var/lib/dns-override-bot/` — формат бот
меняет свободно. Примеры: `dns-override-telegram-bot/state-examples/`.

## D2. Формат — компактный текст, не бинарь и не JSON

**Решение.** Строка заголовка JSON + по строке на правило (`WO0 com.google`),
тело отсортировано побайтово.

**Почему.**
- Читаемость для человека не нужна (вся работа через бота), но **отлаживаемость** нужна:
  `head`, `grep`, `wc -l` работают по файлу без инструментов.
- Языконезависимость: бот и приложение написаны на разных языках. Текстовый контракт
  невозможно рассинхронизировать на уровне раскладки байт, выравнивания и порядка полей.
- Цена приемлема: 300k правил ≈ 8 МБ, парс ≈ 200–300 мс, и то раз в несколько часов.

**Отвергнуто:** бинарный снапшот с mmap (~50 мс загрузки) — выигрыш 150 мс раз
в несколько часов не стоит жёсткого байтового контракта между Python и C#.
JSON-массив (~30 МБ, парс 1–2 с, высокие аллокации) — проигрывает по всем осям,
а его единственное преимущество (читаемость) не требуется.

## D3. Настройки — в заголовке ruleset

**Решение.** `targets`, `qtypePolicy`, `defaultAction` лежат в JSON-заголовке
того же файла. Правило ссылается на target **по индексу**.

**Почему.** Буквально один конфиг-файл. Смена IP и правка правил применяются одной
атомарной заменой — нельзя поймать состояние, где правило указывает на ещё
не существующий target. Ссылка по индексу вместо имени убирает поиск по словарю
в горячем пути.

**Цена.** Смена одного IP требует перегенерации всего файла. Приемлемо: бот
генерирует его целиком в любом случае.

**Отвергнуто:** держать настройки в `dnsApp.config` (правится из админки Technitium
руками). Даёт аварийную смену IP без бота, но создаёт второй источник состояния
и рассогласование targets. Аварийный сценарий закрыт тумблером `enabled`
в `dnsApp.config`.

## D4. Разбор по длине суффикса остаётся в приложении

**Решение.** Бот не разворачивает wildcard. Приложение ищет самое длинное совпадение
по суффиксу; при точном совпадении домена `apex` бьёт `wildcard`.

**Почему.** Wildcard покрывает бесконечное множество поддоменов — перечислить их нельзя.
Это единственная часть логики, которую физически невозможно унести в компилятор.

Граница проведена так: бот убирает всё, что зависит от **происхождения** правил;
приложению остаётся чистая иерархия доменов, от происхождения не зависящая.
Требование «приложение не знает, как собираются правила» выполнено полностью.

## D5. Тело ruleset отсортировано ботом

**Решение.** Сортировка по `rdomain` побайтово — часть контракта, а не оптимизация.

**Почему.** Приложение не строит дерево: загружает тело как `byte[]` + массив смещений
строк и делает бинарный поиск сравнением `ReadOnlySpan<byte>`. Ноль аллокаций на запрос,
10 МБ памяти на 300k правил против ~40–60 МБ у trie, загрузка вместо построения индекса.
Сортировка на стороне бота бесплатна — он всё равно проходит по всем правилам.

## D6. Записи атомарны, чтение — по событию плюс страховочный опрос

**Решение.** Писатель: `.tmp` → `fsync` → `rename()`. Читатель: `FileSystemWatcher`
на **каталог** + дебаунс 500 мс + `stat` раз в 60 с.

**Почему.** `rename()` атомарен на ext4 — приложение никогда не видит полуфайл,
глобальный лок не нужен. Watcher вешается на каталог, потому что `rename` заменяет
inode и подписка на сам файл умирает после первой записи. Опрос закрывает
монтирования без работающего `inotify` (bind-mount, docker volume, NFS)
и переполнение очереди событий. Дополнительно целостность проверяется
`sha256` и `count` в заголовке.

## D7. Безопасные умолчания при подмене

| Умолчание | Почему |
|---|---|
| Домен вне ruleset → `passthru` | явное требование: ничего вне конфига не подменяется |
| `HTTPS`/`SVCB` → `nodata` | `ipv4hint`/`ipv6hint` иначе утекут и уведут клиента в обход подмены |
| `emptyFamilyPolicy` → `nodata` | нет IPv6 в target — не отдавать реальный AAAA |
| `AD = false`, без `RRSIG` | подменённые данные не валидированы |
| Ошибка загрузки → прошлый снапшот | резолвинг важнее свежести правил |

## D18. Сброс кэша DNS — только вручную и целиком

**Решение.** Кэш DNS-сервера сбрасывает оператор кнопкой «🧹 Сбросить весь кэш DNS»
в разделе «Сервис» бота, вызовом `POST /api/cache/flush`. Автоматического сброса
после применения правил нет ни у бота, ни у приложения. Полей `flushCacheOnReload`
и `flushScope` в заголовке ruleset больше нет.

**Почему.** Приложение сбросить кэш не может в принципе: `IDnsServer` операции
сброса не содержит, а `IDnsServer.DnsCache` — это `IDnsCache` ровно с двумя
методами, `QueryAsync` и `CacheResponse`. Остаётся бот с HTTP API сервера,
и там сброс — заметное действие: он роняет весь кэш резолвера, а не только
подменяемые домены. Решать за оператора, когда это делать, бот не должен;
списки обновляются автоматически по расписанию, и тихий сброс кэша на каждое
обновление списка — не то поведение, которое ожидаешь от фонового процесса.

**Цена.** До истечения TTL уже закэшированных ответов новые правила на этих
доменах не работают. Лечится той же кнопкой.

**Отвергнуто.**
- Точечное удаление через `/api/cache/delete?domain=…` по диффу прошлой сборки:
  требует хранить предыдущий набор правил и делать по HTTP-запросу на домен,
  а при обновлении крупного списка это тысячи запросов.
- Имитация сброса через `IDnsCache.CacheResponse`: не удаляет записи для доменов,
  которые перестали подменяться.

## D19. Порядок среди приложений задаётся `appPreference`

**Решение.** Приложение реализует `IDnsApplicationPreference`, значение берётся
из `dnsApp.config` (`appPreference`, по умолчанию `20`).

**Почему.** DNS-сервер опрашивает обработчики приложений по возрастанию
`Preference`; приложение без этого интерфейса считается за `100`. Подмена должна
отрабатывать раньше приложений общего назначения, при этом на одном сервере может
стоять несколько приложений с пересекающимися доменами — значит порядок обязан
настраиваться, а не быть зашитым. `20` — то же значение, что у штатного NX Domain App.

## D24. `runtime-state.json` — необязательный канал, а не условие работы

**Решение.** Ошибка записи `runtime-state.json` не останавливает ничего и
печатается в журнал **один раз** (и один раз — её исчезновение). Если каталог
из конфига недоступен, файл пишется в каталог самого приложения; основной путь
пробуется при каждой записи, поэтому канал возвращается на место сам, без
перезапуска DNS-сервера. Пустой `runtimeStatePath` выключает запись совсем.

**Почему.** Файл нужен только боту — показать в «📊 Статус», какую ревизию
правил приложение применило. На резолвинг он не влияет вообще, а писался в
общий каталог, который у сервиса может быть смонтирован только для чтения
(`ProtectSystem=` в юните). До этого решения каждая попытка записи давала
трассировку стека в журнале DNS-сервера раз в `pollIntervalSec` — то есть
1440 записей в сутки об одном и том же.

**Отвергнуто.**
- Падать при недоступности файла: подмена DNS работает и без обратного канала.
- Писать только в каталог приложения: бот читает файл с диска и туда не ходит.
- Один раз выбрать путь при старте: тогда выдача прав требовала бы перезапуска
  DNS-сервера, хотя ACL действует немедленно.

## D25. Версия приложения — два числа, тег релиза — `vX.Y`

**Решение.** `<Version>` в `DnsOverrideApp.csproj` — `X.Y`, тег релиза — `vX.Y`.
Приложение отдаёт версию в `runtime-state.json` в том же виде, в каком её
показывает Technitium. Бот при сравнении дополняет числа нулями до одной длины.

**Почему.** Technitium показывает версию приложения без незначащих нулей:
сборка `0.2.0.0` в `/api/apps/list` называется «0.2». Бот сравнивал её с тегом
релиза `v0.2.0`, получал `(0,2,0) > (0,2)` и сообщал о доступном обновлении на
уже установленную версию — бесконечно. Выравнивание чинит сравнение, короткий
тег убирает саму возможность расхождения.

**Цена.** Патч-версии у приложения выражаются третьим числом (`0.3.1`), и такой
тег тоже работает: Technitium покажет «0.3.1», сравнение сойдётся.

## D26. Приложений Technitium может быть много, и задаются они конфигурацией

**Решение.** Бот управляет списком приложений (`config.ManagedApp`): ключ, имя в
админке, репозиторий с релизами, шаблон ассета. Из коробки — DNS Override и
DNS IPCollector; любое другое добавляется переменной `EXTRA_APPS` без правки кода.
Ключ приложения используется в `callback_data` и в `--update-app <ключ>`.

**Почему.** Приложение в Technitium — не одно, и второе (сбор адресов клиентов
в ipset) понадобилось ровно через день после первого. Захардкоженная пара
«бот + приложение» означала бы правку хендлеров, клавиатур, CLI и конфига на
каждое следующее.

**Отвергнуто.** Список приложений в состоянии бота (`settings.json`): это не
пользовательская настройка, а описание окружения — ему место в `bot.env`
рядом с адресом API и токеном.

## D27. Права выдаются одним root-скриптом, а не набором sudo-правил

**Решение.** Всё, что требует root — установка `acl`/`ipset`, `setfacl`,
drop-in для `dns.service` с `ReadWritePaths` и `AmbientCapabilities=CAP_NET_ADMIN`,
`setcap`, перезапуск DNS-сервера, — делает `deploy/access.sh`. Установщик кладёт
его в `/usr/local/lib/dns-override-bot/access.sh` (root:root 0755) и разрешает
боту одной строкой в sudoers.

**Почему.**
- Бот работает без root, а приложение Technitium не может выдать права себе само.
- Разрешить в sudoers `setfacl`, `setcap` и `systemctl` по отдельности — значит
  описать возможности бота комбинациями аргументов. Один скрипт читается целиком.
- Скрипт лежит **вне** каталога обновлений: обновление бота распаковывает
  произвольный архив с GitHub, и оно не должно уметь подменить то, что
  запускается от root.

**Почему drop-in, а не правка `dns.service`.** Установщик Technitium
перезаписывает юнит на каждом обновлении DNS-сервера, а каталог `dns.service.d/`
не трогает — настройка переживает обновление.

**Почему `AmbientCapabilities`, а не `setcap` на `ipset`.** `setcap cap_net_admin+ep`
выдаёт право управлять ipset всем пользователям системы и слетает при обновлении
пакета `ipset`. Ambient-права ограничены одним сервисом и наследуются при `exec`,
поэтому запущенный из сервиса `ipset` их получает. `setcap` оставлен отдельной
кнопкой — для случаев, когда сервисом управляет не systemd.

**Важно.** `ReadWritePaths` и capabilities применяются при создании процесса,
поэтому drop-in требует именно **перезапуска** `dns.service`, а не `daemon-reload`.

## D28. Xray DAT и белые списки в одном ruleset

Бот хранит выбор Xray по URL, формату, имени секции и номеру вхождения. Имена
могут повторяться внутри файла. Изменение количества одноимённых секций
приостанавливает обновление источника и сохраняет его кэш.

Новые политики используют заголовок ruleset версии 2. Старое приложение
явно отклоняет эту версию, а обновлённое читает версии 1 и 2. Формат тела
сохраняется, чтобы обычные правила продолжали использовать бинарный поиск.

Доменный белый список проверяется до выбора любого действия подмены. На
стадии постобработки Technitium может разрешить цепочку CNAME без
авторитативных обработчиков. Для белого списка IP используется тот же
штатный резолв перед подменой, поскольку совпадение зависит от адресов
исходного ответа. Приложение пропускает подмену, если не может безопасно
проверить исходный ответ.
